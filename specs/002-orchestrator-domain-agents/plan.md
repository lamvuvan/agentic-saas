# Implementation Plan: Orchestrator and Domain Agents

**Branch**: `002-orchestrator-domain-agents` | **Date**: 2026-03-18 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification + Agentic_WorkPlan_v2.md (sections 1.1–1.9)

---

## Summary

Build a multi-agent Agentic AI SaaS MVP: an Orchestrator (port 8000) that classifies intent, generates a dual-layer plan, and dispatches tasks to three Domain Agents — Order Agent (8002), BI Agent (8003), Customer Agent (8004) — via an asynchronous A2A protocol. All agents are implemented as LangGraph `StateGraph` pipelines with Redis checkpointing. HITL confirmation for mutating tools uses LangGraph `interrupt_before`. Domain Agents accumulate semantic + episodic memory in PostgreSQL. The Orchestrator accumulates routing memory. Parallel and sequential task dispatch is handled by a `DispatchEngine` that evaluates the `depends_on` graph generated by the Plan node.

**Language/Version**: Python 3.12
**Primary Dependencies**: FastAPI 0.111+, LangGraph 0.2+, LangChain, langchain-openai, langgraph-checkpoint-redis, httpx (async), asyncpg, sentence-transformers (`paraphrase-multilingual-MiniLM-L12-v2`), faiss-cpu, faster-whisper, redis, openai, pydantic v2

**Testing**: pytest, pytest-asyncio, respx (HTTP mocking)
**Target Platform**: Linux server, Docker Compose (4 services)
**Project Type**: Multi-service web application (microservices)
**Performance Goals**: P95 order response ≤ 3 s; P95 BI response ≤ 5 s; voice WER < 15%
**Constraints**: Bearer token MUST NOT be stored or logged; HITL before every mutating tool call; LangGraph interrupt for HITL (not manual pause); `AsyncRedisSaver` for state persistence
**Scale/Scope**: MVP — single tenant, up to 10 concurrent users, < 10k products in FAISS index

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| HTTP REST instead of MCP SDK for Tool Registry | MVP: 4 services on same Docker network, no external MCP clients. Adding `mcp` SDK and transport layer increases dependency surface for no functional gain at this scale. | MCP SDK adds `stdio`/SSE transport complexity; debugging requires understanding transport internals vs `curl`. ## Phase 1: Design Artifacts

### LangGraph Graph Topology (key flows)

**Orchestrator**:
```
START
  └─► classify_intent (GPT-4o-mini)
        ├─[chitchat]─► chitchat (GPT-4o-mini) ─► respond ─► END
        └─[else]─────► plan (GPT-4o)
                          └─► dispatch (DispatchEngine)
                                └─► respond (GPT-4o-mini) ─► END
```

**Order Agent** (with HITL):
```
START
  └─► extract_entities ─► match_products ─► check_customer ─► preview_order
        ◄─────────────────────────────────────────────────────[not ready]
        └─[ready]─► [INTERRUPT: hitl_confirm] ─► create_order ─► done ─► END
```

**Customer Agent** (with HITL for write ops):
```
START ─► retrieve_memory ─► classify_action
                               ├─[lookup]──► lookup_customer ─► done ─► END
                               ├─[create]──► prepare_create ─► [INTERRUPT: hitl_confirm] ─► create_customer ─► done ─► END
                               └─[update]──► prepare_update ─► [INTERRUPT: hitl_confirm] ─► update_customer ─► done ─► END
```

**BI Agent** (no HITL):
```
START ─► retrieve_memory ─► nl2sql ─► safety_check ─► execute_query ─► format_result ─► done ─► END
```

### A2A Task Resume Flow

```
1. Domain Agent graph reaches interrupt_before=["hitl_confirm"]
2. Graph state (with confirm_message) serialized to Redis
3. A2ATask.status = "input_required", input_request = state["confirm_message"]
4. Orchestrator returns confirm_message to user
5. User responds → Orchestrator POSTs continuation to Domain Agent
6. Domain Agent calls:
   compiled.ainvoke(
       Command(resume={"user_confirmation": user_response}),
       config={"configurable": {"thread_id": task_id}}
   )
7. Graph resumes from exact checkpoint, continues to create_order / create_customer / update_customer
```

## Key Implementation Notes

### 1. LangGraph HITL Pattern (critical)

```python
# Compile with interrupt
compiled = graph.compile(
    checkpointer=AsyncRedisSaver.from_conn_string(REDIS_URL),
    interrupt_before=["hitl_confirm"]
)

# First invocation — runs until interrupt
result = await compiled.ainvoke(
    OrderAgentState(...),
    config={"configurable": {"thread_id": task_id}}
)
# → graph halts, state saved to Redis, returns partial state
# → a2a_server sets task.status = "input_required"

# Resume after user confirms
result = await compiled.ainvoke(
    Command(resume={"user_confirmation": user_response}),
    config={"configurable": {"thread_id": task_id}}
)
# → graph resumes from hitl_confirm, proceeds to create_order
```

### 2. Orchestrator Message Accumulation

```python
class OrchestratorState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
    # add_messages reducer: new messages are appended, not replaced
    # Previous turns persist in Redis checkpoint across requests
```

### 3. BI Agent Stateless Execution

BI Agent uses `MemorySaver` (not Redis) because:
- No HITL interrupt — task completes in one invocation
- BI queries are fast (< 5s) — pod restart during a BI task is acceptable to retry
- Avoids Redis write overhead for read-only tasks

### 4. Plan Persistence Before Dispatch

```python
# In plan node — MUST persist to PostgreSQL before returning
plan_id = await plan_service.create_plan(session_id, tenant_id, user_message, display)
return {**state, "plan_id": plan_id, "plan": {"display": display, "routing": routing}}
# dispatch node reads plan_id and routing steps
# Satisfies Constitution V (plan persisted before execution)
```

### 5. DispatchEngine — Parallel vs Sequential

```python
# Steps with depends_on=[] → dispatched concurrently via asyncio.gather
# Steps with depends_on=["order-agent"] → wait for upstream, inject dependency_results
ready = [s for s in remaining if all(dep in results for dep in s.get("depends_on", []))]
dispatched = await asyncio.gather(*[dispatch_one(step, ...) for step in ready])
```
